1. Three differences between my laptop and CI: cold cache, no .env, and no Ollama model. For the cache, frontend/Dockerfile copies package.json and package-lock.json before RUN npm ci and before COPY . ., so the dependency layer can still be reused on a fresh runner. For the .env, ci.yml sets DATABASE_URL, REDIS_URL and TRIAGE_PROVIDER as job env: values pointing at the throwaway service containers. For the model, a laptop has Ollama's model pulled and a runner doesn't, so every test job pins TRIAGE_PROVIDER: simulated.

2. We're at automated CI with a gated deploy. ci.yml blocks merges on lint, types, tests, image build, Trivy, manifest validation and a Compose integration test, and cd.yml only runs from main. It isn't full continuous deployment because main needs a PR approval. The next rung is progressive delivery (canary with automatic rollback on real metrics). It would make releases safer, but it needs weighted-routing infrastructure we don't have.

3. The guarantee is in frontend/nginx.conf, where /api/ is proxied to a service named backend (ADR 0002), so nothing environment-specific is baked into the image. The backend gets its config through envFrom in k8s/base/backend.yaml. Without this we'd need VITE_API_URL at build time, one image per environment, and the image tested in CI wouldn't be the one running in prod. That would defeat the SHA-pinning in ADR 0003.

6. k8s/base/vpa.yaml uses updateMode: "Off". Our HPA scales on CPU utilization, which is usage divided by request. If VPA ran in Auto, it would raise the request, so utilization drops and the HPA scales in. Fewer pods means more load per pod, so VPA raises the request again, and the two keep chasing each other without settling. In Off mode we read the recommendations and change requests ourselves.

7. An internal: true network has no route out, so a service only on it can't reach Groq. We made backend the only service on both networks (compose.yaml, networks: [edge, internal]), using internal for Postgres and Redis and edge for the outbound call. One gap: the Kubernetes manifests have no NetworkPolicy, so egress is open by default. We'd add one denying frontend egress and restricting Postgres and Redis ingress to app: backend, but we ran out of scope.
